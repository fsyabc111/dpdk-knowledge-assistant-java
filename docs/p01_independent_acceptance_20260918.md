## 按严重程度排序的问题

以下行号均指本轮 HEAD。独立反例在原始 P0.1 快照和当前 HEAD 得到相同结果，日志见 `reproduce-original.log`、`reproduce-current.log`。这些问题不全部由 P0.1 引入，已逐项区分。

### F1 严重：最近一次已完成评分的源码副本仍能造成虚假的“地板超限”

位置：`backend/app/agent/context.py:180`、`:184`、`:213`、`:289`。

L3 无条件跳过最后一个工具单元的长参数，L5 又保护该单元。已经执行完的 `grade_plugin.plugin_source` 仍不能压缩或删除。独立反例：系统提示 10,000 字符、用户消息 9,000 字符、已完成评分的源码参数 9,000 字符、短评分结果，预算 24,000；返回 `over_budget=true`、`prepared_chars=28119`、`reason=floor_exceeded`，但真正的“系统 + 当前请求”仅 19,000。

这是 P0.1 新分级算法的收敛缺口，不是合理的请求本身超限。应在已完成工具调用和待执行调用之间区分参数保留规则；现有 `prep05b` 只测试评分已成为旧轮的情况。

### F2 严重：SSE 已输出少量文字后降级，会丢弃已完成评分

位置：`backend/app/agent/service.py:441`、`:452`、`:458`。

只有 `answer_parts` 为空才追加确定性评分。把黄金 s33b 的首个模型消息从空文本改成正常的“我先检查这份插件。”，其余条件不变：MCP 成功评分一次，随后触发预算降级，最终正文只有这句前置说明，没有 62 分、5/8 或失败用例。事件为 `status/start/status/delta/tool_start/tool_end/error/done`，仍以 `stream_status=completed` 落库。

评分摘要曾出现在 `tool_end` 不等于正文保留评分与期望/实际差异。P0.1 对空输出路径的修复成立，但未覆盖流式已有输出这一分支；`:934` 开始的 s33b 没有模拟该情况。JSON 与 SSE 的降级语义因此不一致。

### F3 严重：finalize 仍收到无结果配对的 tool_call

位置：`backend/app/agent/graph.py:164`、`:183`、`:185`；`backend/app/agent/context.py:94`。

达到轮数或 token 上限时，最后一条 planner 消息提出的工具调用没有执行，却原样送进 finalize。独立图运行在 `max_rounds=1` 时，finalize 输入有 `c_kb`、`c_kb2` 两个调用，仅有 `c_kb` 的 ToolMessage。压缩保持了已有配对，却没有修复这个入口本来就不完整的序列。

这是原有路由缺陷，P0.1 的统一准备管线未闭环它；“永远没有悬空 tool_call”的说明不成立。严格校验工具协议的兼容端可能拒绝该请求，本轮没有额外付费探测这种拒绝。既有 finalize 测试只验证体积与附注，脚本化模型不会拒绝不配对的消息。

### F4 严重：模型的片段编号与响应 citations 编号不一致

位置：`backend/app/agent/service.py:334`、`:339`、`:346`；对照 `backend/app/agent/tools.py:128` 的片段编号。

工具按片段顺序发 `[n]`，响应却按文件去重且最多保留四条。反例：模型收到 `a1(a.md), a2(a.md), b1(b.md)`，答案引用 `[2]` 表示 a2，响应第二条却是 b1。编号身份已经改变，压缩摘要保留 ref 并不能解决它。

这是既有缺陷，不宣称为 P0.1 新回归。当前 live 第一轮 `route_kb_engine_ops` 也实测出现 `[9][10][17][18]`，而 sources 只有四项；词条判定 PASS 并不代表引用验收通过。

### F5 中等：降级源码消毒仅覆盖反引号围栏

位置：`backend/app/services/agent_service.py:42`、`:63`、`:110`。

裸粘贴的 `int STUDENT_SECRET(void){return 7;}`，或 Markdown `~~~c` 围栏，都会完整出现在降级问题预览中。120 字符上限不能避免短源码全文回显。P0.1 修好了三反引号用例，但没有实现一般的“不回显学生源码”要求。

另外，`backend/app/agent/service.py:167` 在无附件时直接持久化 question；粘贴源码仍进会话正文。这是已有的源码最小化缺口，不是本轮新引入的数据库回归；上传路径的附件标记及成绩表 hash 存储不能证明粘贴路径也最小化。

### F6 中等：压缩后的评分摘要鼓励重评，运行时没有同请求去重

位置：`backend/app/agent/tools.py:546`、`:242`、`:254`。

新增摘要写明“需要完整逐用例结果可重新评测”。若模型在后续轮请求相同协议与源码，工具仍再次调用 MCP、再次扣学生配额、再次记录成绩。独立反例中相同成功评分执行两次。

异常兜底本身没有自动重试，已完成评分后直接抛异常的原黄金场景确实只执行一次；不能把这个窄结论扩大成压缩后继续规划也不会重复评分。无去重是既有风险，新提示放大了该风险。本轮没有把它误报为 MCP 传输层重试。

### F7 中等：完成报告对原五个失败的表述过强

位置：`docs/next_stage_plan.md:36`；`docs/next_agent_handoff.md` §4。

原报告明确是 6/11；探针 4/5；正式复测 10/11。`route_kb_engine_ops` 在三份报告中始终 FAIL，因此“4 项预算失败与 1 项围栏越界全部转 PASS”与原始结果不符。可以说预算异常有改善，不能说原五题全部通过。旧正式答案的 `process` 仅被子串口径满足，独立按词边界复核仍缺 `process` 和 `can_handle`。
