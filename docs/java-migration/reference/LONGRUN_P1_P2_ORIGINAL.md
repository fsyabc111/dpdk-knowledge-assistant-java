## 当时的任务书

```text
你是 DPDK Knowledge Assistant Java 迁移项目的主Agent。

本任务书替代上一版“只执行P1、11:50截止”的安排。
当前先核对仓库、依赖与执行计划并结束一轮；收到我随后发送的
/goal 启动指令后，按以下授权连续执行。

一、目标与授权

本次预授权P1和P2作为一个连续批次：
- P1：J1-01、J1-02、J1-03、J1-04。
- P2：J2-01、J2-02、J2-03、J2-04、J2-05。

允许主Agent在P1工程门禁通过后自动进入P2，无需等待我中途确认。
工程门禁不等于用户验收；用户验收由我在批次结束后统一进行。

取消原11:50硬截止。中午是进度检查点，任务以P1/P2目标达成收口。
提前完成就结束，不为填满时间继续扩范围。

允许必要开发依赖、独立测试PG、合成数据、本地模型/MCP替身、
必要验证、功能分支集成、正常提交和及时推送。
允许新副本中React与Java联调所需的最小测试接线，由集成者单写。

禁止进入P3及后续阶段、合并main、部署、修改原项目/原部署/业务库、
调用项目真实模型/embedding/评测服务或删除恢复资产。

二、仓库与起点

目录：
/Volumes/study/code/new_project/dpdk-knowledge-assistant-java

远程：
https://github.com/fsyabc111/dpdk-knowledge-assistant-java.git

已验收P0起点：
codex/p0-baseline-oracle
d982f3affa662e5adc6b38a38879d7d1dc1440a6

从已验收P0建立本次集成分支，建议：
codex/p1-p2-longrun

若已有后续变化，先读新增交接，不reset、不覆盖他人工作。

三、读取与状态

先读AGENTS.md、START_HERE.md、STATUS.md、handoffs/MAIN.md、
migration/contracts/P1_HANDOFF.md，再按需读PLAN和当前任务卡。

开始实施时把本次直接用户授权及P1→P2条件写入STATUS/DECISIONS。
STATUS是唯一任务状态；Goal面板和聊天总结不能替代仓库证据。
旧Python roadmap/archive不是Java执行队列。

四、依赖与阶段门禁

P1：
J1-01先交付可构建工程、隔离配置、公共端口和单一迁移链；
通过后并行J1-02和J1-03，最后J1-04集成。

进入P2前必须：
- P1任务卡强制条件均有实际验证；
- 独立测试PG与危险目标拒绝检查通过；
- 协议替身、固定向量和最小问答链路通过；
- 独立规范/规格审查完成，阻断问题修复并复验；
- P1报告、交接与提交已推送并核对SHA。

记录为“P1工程门禁通过，用户验收待进行”，再按预授权进入P2。

P2：
J2-01认证 → J2-02管理员/班级树 →
J2-03作业/成绩/CSV与J2-05会话/配额/用量并行 →
J2-04正式提交与替身评测 → 集成回归。

只有PLAN明确列出的P3接线项允许integration_pending；
必须有契约测试、责任卡和补验说明，不能写成实际接线已通过。

五、协作与所有权

最多同时3个子Agent。每次派工给出：
任务、基线、契约版本、独占写路径、只读路径、依赖、
验收条件、证据位置和停止条件。

主Agent负责STATUS/MAIN、公共构建/配置、接口协调、
单一DDL所有权、集成及最终发布。

子Agent优先使用独立worktree；共享文件不得并发修改。
审查使用独立上下文，修复交回原owner。
子Agent回报不超过500字，完整证据落文件。
不要让两个主会话同时修改同一工作区。

六、及时提交与推送——本批次强制要求

不能等P1或P2大阶段结束才统一推送。

以下时点形成有意义的提交并及时正常推送：
1. 独立子功能初步实现、达到可审查状态；
2. 一批测试修复完成；
3. 一批评审修改完成；
4. 集成切片及验证完成。

任务卡过大时拆内部子切片，不增加无关范围。
每30—60分钟检查是否有应提交未提交、应推送未推送的成果。
不制造空提交，不为记录自己的提交SHA递归制造提交。

未完成全部测试也可以推送开发分支，但明确：
验证到哪一步、哪些失败/未运行、下一步是什么。
不可构建的中间成果保存在独立工作分支并标WIP；
集成分支优先接收可构建快照。

只有集成者操作主集成分支的提交/推送。
每次只提交当前任务文件，检查敏感信息、原始日志和运行输入。
推送后核对本地HEAD与对应远程分支SHA。
不force push，不合并main，不触发生产部署。

推送失败先保存本地提交、记录并诊断，不伪称已发布。
最终完成必须包含远程一致性核验及干净的集成工作区。

七、验证与兼容

技术栈、接口、身份、计分、权限、SSE、引用及数值门槛
遵守已冻结的P0契约和决策。

PG启动先验证目标身份；禁止.env/default DB回退。
P0黄金只读，不用Java输出反向改黄金，不降低断言换绿色。
只替换外部模型/embedding/MCP边界，不伪造最终业务结果。

测试对应实际代码提交或内容摘要。
实现、自动验证、合成场景、用户验收分开记录。
未运行、skip、blocked不计通过。

P2必须验证真实Java+独立PG的业务闭环：
三模式认证、班级权限、作业CRUD、替身评测提交、
配额与成绩副作用、成绩汇总/CSV、会话/用量/来源读取。
页面联调与API/PG证据分别记录。

八、进度、阻塞与恢复

每个子切片、关键决策和上下文压缩前更新状态与MAIN；
长任务至少每30分钟保存一次有实质内容的恢复点。
记录owner、分支/提交、未提交文件、进程/端口及下一准确动作。

常规工程选择自主处理，不逐文件询问。
影响产品行为、数据兼容、权限或验收标准的重大取舍，
记录后封锁相关工作，等待用户，不把问题超时当批准。
继续推进不依赖该决定的安全任务。

同因失败没有新证据时不反复空跑。
全部剩余工作确实受用户决策或不可用环境阻塞时，
保存证据并暂停，保持未完成状态，不伪造阶段通过。

九、最终交付

- P1与P2各自的phase-report.md；
- 更新后的STATUS、DECISIONS和MAIN；
- 九张任务卡的handoff；
- 实际构建、启动、PG集成、差分和页面场景命令；
- 独立规范/规格审查及关闭证据；
- 已推送分支、提交SHA和远程一致性；
- 未验证项、P3待接线项、运行资源与回退说明。

完成P1/P2后停止，不自动进入P3。
```
